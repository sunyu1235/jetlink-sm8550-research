# QNN 2.42 / HTP v73 custom FP16 GELU lookup: build-path research

**Scope:** read-only feasibility review for a possible HTP custom-op fallback. No SDK was downloaded, no system component installed, and no phone/app state was changed. Research is limited to Qualcomm documentation and Qualcomm-authored ISA references. Current QAIRT docs were consulted on 2026-11-01; current-version statements are not assumed to describe SDK 2.42.

## Findings at a glance

A technically plausible route exists through the **legacy HTP OpPackage API**: Qualcomm documents an FP16 OpPackage example, HTP v73 package builds, an x86 host-side package, and the Qualcomm Hexagon toolchain as separate build dependencies. This supports feasibility in principle, but the public current docs do **not** establish the exact Hexagon SDK/tools pairing or exact FP16 sample source for QNN 2.42. For a 2.42 runtime, the safe route is to obtain the matching 2.42 SDK package and rebuild the legacy package with its own headers/generator; do not compile against current headers and assume compatibility.

A 65,536-entry FP16-bit-pattern map with 16-bit outputs occupies **131,072 bytes (128 KiB)**. Qualcomm's HVX reference documents `vlut16`, but describes an in-lane lookup over a vector table (small table), not a direct 128-KiB table lookup. Thus direct arbitrary indexing into a 128-KiB table from each HVX lane is **not established** by the cited instruction reference. A custom kernel could potentially perform scalar indexed loads or a multi-stage lookup, but memory access, scheduling, table placement, latency, and support in the HTP OpPackage API need an actual v73 build/probe.

## Source-backed facts

- Qualcomm's current HTP backend documentation lists both **“QNN HTP Op Package - Relu Op Example”** and **“QNN HTP-FP16 Op Package - Relu Op Example”**, plus API/header, implementation, scratch-buffer, scheduling, and tensor-layout references. It says legacy packages use macro-based APIs and **must be recompiled after every QNN SDK release**. QHPI is explicitly marked Beta in the current documentation. ([HTP backend and OpPackage documentation](https://docs.qualcomm.com/bundle/publicresource/topics/80-63442-10/htp_backend.html))
- The same documentation describes HTP float execution as FP16 math on select Qualcomm SoCs. It also says HTP converts client FP32 inputs to FP16 and returns FP32 outputs; the documentation states HTP does not support FP32 math. ([HTP precision section](https://docs.qualcomm.com/bundle/publicresource/topics/80-63442-10/htp_backend.html))
- Qualcomm's custom-op tutorial uses `make htp_v73 htp_x86`, references `$HEXAGON_SDK`, `$QNN_INCLUDE`, and an x86 cross/host compiler, and registers a target HTP package. Its sample package path is `examples/Models/InceptionV3/InceptionV3OpPackage/HTP/ReluOpPackage`. This is a concrete current documented v73 build shape, not proof that the same tutorial files were in QNN 2.42. ([HTP custom ops tutorial](https://docs.qualcomm.com/nav/home/htp_auto_tutorial_3_la_gvm.html?product=924033590759186372))
- Qualcomm's current Linux setup says the QNN SDK is about **2 GB unzipped**, and directs users to QPM3, Qualcomm sign-in, and separate Hexagon SDK / Hexagon Tools downloads. Its current compatibility table lists **HTP V73 → Hexagon SDK 5.5.5 and Hexagon Tools 8.7.06**. This is current documentation, not a verified QNN 2.42 pairing. ([Linux setup and toolchain table](https://docs.qualcomm.com/bundle/publicresource/topics/80-63442-10/linux_setup.html?product=1601111740010412))
- Qualcomm's official Software Center currently advertises a 2.50 Community Edition package (about 2 GB zipped in its listing), not the requested 2.42 version. The QNN product page provides “Get Software” and links a product license agreement; download access is routed through Qualcomm's software channels. ([Software Center catalog](https://softwarecenter.qualcomm.com/catalog/item/Qualcomm_AI_Runtime_Community), [QNN SDK product page](https://www.qualcomm.com/developer/software/qualcomm-ai-engine-direct-sdk?redirect=qdn), [Hexagon NPU SDK page](https://www.qualcomm.com/developer/software/hexagon-npu-sdk))
- Qualcomm's HTP page names QHPI Beta, but its legacy API documentation remains listed alongside it. The QNN API revision table maps API 2.32 to SDK 2.42.0; this is QNN API-version history, not an OpPackage-specific compatibility guarantee. ([QNN API revision history](https://docs.qualcomm.com/nav/home/general_api_version_history.html?product=924033590759186372))
- Qualcomm's Hexagon HVX reference documents `vlut16` as an **in-lane table lookup** using a vector table. The V66 manual describes the table as 128 bytes in 128B mode and explicitly says lookup variants that ignore higher index bits are for small tables. This demonstrates a vector lookup primitive but does not demonstrate an efficient 64K-element memory gather, nor establish exact V73 compiler/library behavior. ([Hexagon V66 HVX Programmer's Reference Manual](https://docs.qualcomm.com/bundle/publicresource/80-N2040-44.pdf), [V60 HVX Instruction Quick Reference](https://docs.qualcomm.com/doc/80-N2040-35/80-N2040-35_REV_B_Hexagon_V60_HVX_Instruction_Quick_Reference.pdf))

## Assessment: facts vs inference vs unknowns

### Inference

- **Windows + Android NDK 30 alone is not a sufficient demonstrated build setup.** The Qualcomm HTP custom-op example requires a Hexagon-target build (`htp_v73`) and explicitly consumes the Hexagon SDK; NDK is the Android ARM target toolchain and does not supply the documented Hexagon compiler/toolchain. A native Linux host is the lowest-risk documented route. Qualcomm's current Linux setup uses a Linux SDK workflow; no Windows host path for HTP OpPackage compilation was established here.
- **QNN 2.42 should use its legacy HTP package API and matching generated build files/headers.** Qualcomm says legacy packages need recompilation for every QNN SDK release. Even if the source API remains similar, reuse of a package compiled against another release should not be presumed safe. Current QHPI Beta guidance cannot be projected backward to 2.42.
- A 128-KiB static LUT can fit as a read-only data object in principle, but this does not guarantee that the HTP package linker/runtime accepts or efficiently serves it from the DSP memory hierarchy. The documented `vlut16` primitive alone cannot implement arbitrary 16-bit indexing into all 65,536 entries in one instruction; likely options would involve indexed loads, staged decomposition, or another kernel implementation. These are performance/implementation hypotheses, not Qualcomm-confirmed recipes.
- The existing CPU exact-GELU bit-pattern LUT is a strong numerical reference for a custom op, but an HTP implementation must additionally define NaN/Inf/signed-zero behavior and ensure that tensor pointers are actually half payloads as expected by that graph/package configuration. The public page reviewed does not settle all bit-pattern semantics.

### Not verified publicly for QNN 2.42

- The exact downloadable **QNN 2.42 package** and its bundled HTP-FP16 Relu example files / op-package generator revision.
- The exact Hexagon SDK and Tools release pair that Qualcomm certified with **QNN SDK 2.42 + HTP v73**. The current docs pair v73 with SDK 5.5.5 and Tools 8.7.06, but this cannot be labeled a historical 2.42 pairing without the 2.42 release package or release notes.
- Whether the HTP v73 custom-op ABI in the actual phone runtime accepts the proposed FP16 tensor signature, constant table format, and exact static-data size without extra linker or memory constraints.
- Whether the full 128-KiB table can be efficiently indexed from a custom kernel, or whether the HTP compiler/runtime offers a supported table/gather intrinsic or memory region suitable for it.
- Exact sizes of the Hexagon SDK and Tools downloads, and whether the relevant 2.42 downloads remain available to this account. Qualcomm's public docs did not provide those package sizes. QPM3 sign-in is required by the current documented workflow; the precise license/entitlement terms for historical packages were not checked.

## Recommended low-risk build path if the standard-op route remains blocked

1. From Qualcomm's software portal, locate the exact **QNN SDK 2.42.0** and its release notes/package contents. Confirm it contains the legacy HTP OpPackage API and FP16 example before selecting any toolchain.
2. Determine the historical v73 Hexagon SDK + Tools pair from that package's release notes or Qualcomm's version-matched docs. Do not infer it from the current 5.5.5 / 8.7.06 table.
3. Use an isolated native Linux build environment (or a Linux machine) with the matching QNN 2.42 package and Hexagon compiler. Build both `htp_v73` and the host `htp_x86` package targets as Qualcomm's tutorial does; keep the Android app and system libraries untouched.
4. Start with a tiny FP16 identity/table-slice op and compile/load it on HTP v73. Then test a limited LUT (e.g. selected bins) and measure per-op output against the CPU reference before attempting the full 65,536-entry map.
5. For the full lookup, separately measure model/context size, initialization cost, per-element latency, output exactness including special values, and interaction with existing EPContext partitioning. A 128-KiB array has a small file footprint relative to the model, but its access pattern may dominate runtime.

## Practical conclusion

**Build feasibility: plausible, version-matched confirmation required.** Qualcomm provides the right class of legacy HTP custom-op interface and a documented FP16 example, and its current tutorial includes a v73 target. The host's NDK does not replace the Hexagon SDK. The most substantial technical uncertainty is not the LUT byte count; it is whether a 128-KiB arbitrary-index table can be implemented efficiently and reliably in an HTP v73 custom kernel. Treat this as a fallback experiment, not yet a drop-in replacement for the already validated CPU GELU path.
