# Moto X40 Light Speed baseline — 2026-10-31

Device XT2301-5, SM8550, Android 14 U1TR34.8-19-11, Magisk 31.1. Jetlink Android 0.8.12, LiteRT 2.2.0 GPU FP16. Light Speed ONNX SHA-256 6274eb4a3f3eb7ad1ab341d222bbba2ba709b06645dbbd15ac4971d6cb22ab21 (792305602 bytes), exported as f22b8b34/16384. Loaded as a local model.

- Screen on baseline, 60 s while charging: mean 96.2 ms, p99 112.4 ms, maximum 123.5 ms, 621 frames, 621 above 50 ms. Model mean 96.0 ms. At start GPU clock observed 680 MHz and GPU busy approximately 90%; later 550 MHz and thermal_pwrlevel 2. Temperatures, charging, and starting conditions were not controlled.
- Android fixed-performance mode: cancelled at 13 s, mean 174.4 ms, p99 179.9 ms, 75 frames, GPU observed 348 MHz. Fixed-performance mode was disabled after the trial.
- Screen off after the preceding workload: mean 110.3 ms, p99 138.4 ms, 541 frames over 60 s. Screen on immediately afterwards: cancelled at 51 s, mean 134.6 ms, p99 139.2 ms, 374 frames. The temperatures differed, so these are not a controlled screen-on/off comparison. GPU temperature node peaked at an observed 67.8 C with clock 475 MHz; continuous tests were stopped to cool.
- TCP over Wi-Fi: 20 deterministic synthetic road-like inputs, server report mean 97.71 ms, round trip mean 133.14 ms, p99 204.21 ms; all 20 replies reported NOT_FINITE. Response was not a valid full-output frame, so this is not an end-to-end camera or usable-model latency measurement. Windows client used a temporary sendmsg fallback. PC was on 5 GHz WLAN and phone on 2.4 GHz WLAN.
- For the same first deterministic synthetic input, original ONNX CPU reference produced 18452 finite values, while the phone GPU returned NOT_FINITE. No output equivalence is established. Benchmark timing alone does not verify output correctness.
- ONNX contains 1004 nodes, including 162 MatMul and 103 LayerNormalization. The converter reported 2919 LiteRT operators. MatMul weight inputs sum to approximately 735 MB (counted per input use), not a profile of actual traffic or execution time.

The first next step is an independently controlled repeat with cooling and matched starting temperatures; investigate matrix and normalization kernel execution with GPU profiling before changing graph conversion or disabling system services.

## NPU and native shared-memory tests

- Same Light Speed ONNX (SHA-256 above), QNN HTP v73 / ORT 1.29.0. Jetlink NPU, CPU keep-awake off: 60 s, mean 37.0 ms, P99 42.2 ms, maximum 45.1 ms; 1,201 frames, none over 50 ms. With CPU keep-awake on: mean 35.9 ms, P99 41.9 ms, maximum 50.2 ms; 1,201 frames, one over 50 ms. These are synthetic benchmark frames; correctness was not validated.
- QNN context graph contains one EPContext node and no remaining standalone CPU nodes; this does not expose internals of the QNN context.
- Basic QNN profiling: median accelerator execute ~31.0 ms, median QNN execute ~37.1 ms; profiling changes performance, and this is not a direct no-profile timing.
- Independent native QNN runner, same compiled context and alternating frame-to-frame state buffers, 20 Hz, 1,200 frames: ordinary memory mean 38.054 ms, P50 37.838 ms, P99 42.810 ms, max 44.929 ms; shared memory mean 32.115 ms, P50 32.071 ms, P99 33.078 ms, max 34.194 ms. Both had zero frames over 50 ms and the final output had 0 nonfinite values among 18,452. The speed comparison is about 15.6% improvement; these are synthetic all-zero input frames, not Jetlink end-to-end, and no parity test was performed.
- Shared-memory experiment used an isolated copy of ORT that resolves remote_register_buf_attr2 to the device's older remote_register_buf_attr symbol. This assumes compatible argument/semantics for this limited test; it is not proven safe or integrated into the Jetlink APK. Device system libraries and installed app files were not replaced. The shared allocator without this compatibility patch failed to initialize due to the missing symbol.
- RPC control latency 100 us and CPU affinity were short tests and did not yield a repeatable improvement. Root and processor controls remain subject to system thermal protections; no overclock was applied.
- Sources: qnn_context_probe.c, qnn_jl_shared.c, jl_ort.h and adreno_gemv_probe.c beside this report. The compiled ONNX context remains in Jetlink's app data on the phone. qnn-profile-basic.csv and qnn-profile.csv are instrumented profiles. The standalone runner and patched ORT copy are experiments, not an installed optimized Jetlink version.
- Additional shared-memory native run: same fixed synthetic road-like image converted to FP16, valid traffic/action scalars, alternating recurrent state buffers, 20 Hz, 1,200 frames: mean 32.475 ms, P50 32.431 ms, P99 33.437 ms, max 34.253 ms, no frame >50 ms. Final driving output had 0 nonfinite values of 18,452. This is repeated synthetic input, not live camera data, and excludes Jetlink staging, communication, and full numeric parity validation.

## 2026-11-01 preliminary output parity
Five identical synthetic road-like frames with recurrent state and matching traffic/action inputs compared the shared-memory QNN runner to ONNX Runtime CPU. All outputs finite. Upstream verify_parity.py reported FAIL: lead on frame 4 and pooled lane_lines, plan and road_edges violated correlation or error limits. Frame 4 lead max absolute difference 4.1641, correlation 0.997968. Overall frame correlations ranged 0.998446 to 0.999917. This is a short repeated synthetic input, not a representative driving validation.
